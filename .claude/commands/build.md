요청: $ARGUMENTS

아래 순서로 에이전트를 사용해 진행하세요. 각 단계 결과는 다음 단계에 그대로 전달합니다.

1. **planner**: 요청의 진짜 목적, 옵션, 추천안, 성공 기준을 받는다.
   - 방향이 둘 이상으로 갈리고 사용자 선택이 필요하면 추천안과 함께 사용자에게 짧게 묻고 멈춘다. 아니면 계속한다.
2. **architect**: 추천안을 구현 설계로 바꾼다 (재사용, 효율, 실패 설계, 테스트 방법).
   - planner와 architect 의견이 충돌하면 근거를 비교해 하나를 택하고 이유를 기록한다.
3. **developer**: 설계대로 구현하고 TS 전체 검사 + 스텁 테스트를 실행해 결과를 보고한다.
4. **reviewer**와 **qa**를 병렬로 실행한다. 각자 변경 내용과 성공 기준을 받고, developer의 보고를 믿지 않고 직접 확인한다.
5. 지적(치명/중요)이 있으면 **developer**가 수정하고 4단계를 다시 한다. 최대 3회. 3회 후에도 남으면 남은 문제를 그대로 사용자에게 보고한다.
6. 통과하면 커밋 → pull → 푸시 (CLAUDE.md 규칙, 커밋 문구 끝 Co-Authored-By).
7. 사용자 보고(한국어, 짧게):
   - 무엇을 왜 그렇게 만들었나 (선택한 방향과 버린 대안 한 줄)
   - 검증한 것 / **확인 못 한 것**(실제 API·화면)과 사용자가 확인할 방법
   - reviewer·qa가 잡아서 고친 문제가 있었다면 한 줄

작은 수정(문구, 한 줄 버그)에는 이 절차를 쓰지 말고 바로 처리하세요.
